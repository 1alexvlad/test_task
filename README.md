# Асинхронное REST API приложение (Эмуляция платежного шлюза)

Данный проект представляет собой реализацию тестового задания.
* **Ссылка на техническое задание:** [Google Docs](https://google.com)

## О проекте
Приложение эмулирует работу финансового бэкенда, взаимодействующего со сторонней платежной системой через вебхуки. Оно поддерживает разграничение прав доступа (Пользователь / Администратор), управление учетными записями, автоматическое создание счетов при первом пополнении и защиту от повторного начисления средств.

### Стек технологий:
- **Язык разработки:** Python 
- **Веб-фреймворк:** FastAPI 
- **Управление зависимостями:** `uv` 
- **База данных:** PostgreSQL
- **ORM:** SQLAlchemy + asyncpg
- **Миграции:** Alembic
- **Контейнеризация:** Docker, Docker Compose
- **Безопасность:** JWT (Access + Refresh токенизация с ротацией в базе данных, HttpOnly Cookies)

## Инструкция по запуску

Перед запуском любым из способов создайте в корне проекта файл `.env` и заполните его по следующему шаблону:
```env
POSTGRES_USER=postgres
POSTGRES_PASSWORD=your_secure_db_password
POSTGRES_DB=wallet_db
SECRET_KEY=gfdmhghif38yrf9ew0jkf32
DATABASE_URL=postgresql+asyncpg://postgres:your_secure_db_password@db:5432/wallet_db
```

### Вариант 1. Запуск через Docker Compose (Рекомендуемый)
Этот способ не требует установленного Python на вашей машине. Всё развернется автоматически одной командой.

1. Убедитесь, что у вас запущен Docker Daemon.
2. Выполните команду в корне проекта:
   ```bash
   docker compose up --build
   ```
3. Docker Compose сам соберет образ приложения с помощью менеджера `uv`, запустит PostgreSQL, дождется готовности базы данных, применит миграции Alembic (наполнив базу тестовыми юзерами) и поднимет FastAPI сервер.

Приложение будет доступно по адресу: **`http://127.0.0.1:8000/docs`**

### Вариант 2. Локальный запуск (Без Docker)
Для этого варианта вам понадобится установленный PostgreSQL на вашем компьютере.

1. Создайте локальную базу данных в PostgreSQL (например, `wallet_db`).
2. Измените в вашем файле `.env` хост в переменной `DATABASE_URL` с `db` на `localhost`:
   ```env
   DATABASE_URL=postgresql+asyncpg://postgres:your_secure_db_password@localhost:5432/wallet_db
   ```
3. Установите менеджер пакетов `uv` (если еще не установлен):
   ```bash
   pip install uv
   ```
4. Создайте виртуальное окружение и установите зависимости проекта:
   ```bash
   uv venv
   source .venv/bin/activate  # Для Linux/macOS
   # или .venv\Scripts\activate для Windows
   uv pip install -r pyproject.toml
   ```
5. Примените миграции базы данных для создания таблиц и тестовых данных:
   ```bash
   alembic upgrade head
   ```
6. Запустите сервер разработки:
   ```bash
   uvicorn app.main:app --reload
   ```

Приложение будет доступно по адресу: **`http://127.0.0.1:8000`**

## Важные архитектурные решения проекта

В процессе реализации были учтены критические требования к безопасности и отказоустойчивости финансовых систем:
1. **Идемпотентность вебхуков:** Реализована строгая проверка уникальности `transaction_id`. При повторном получении одного и того же вебхука деньги на счет не начисляются повторно, а система возвращает успешный статус `200`, чтобы предотвратить зацикливание запросов со стороны платежного шлюза.
2. **Защита от состояний гонки (Race Conditions):** При изменении баланса кошелька в транзакции используется пессимистичная блокировка строки в базе данных через `.with_for_update()`. 
3. **Безопасность токенов (JWT + Rotation):** Аутентификация построена на парах Access и Refresh токенов. Refresh-токены хранятся в базе в виде SHA256-хэшей и работают по принципу строгой ротации. Токены помещаются в безопасные `HttpOnly Cookies`, что исключает их кражу с помощью XSS-атак.
4. **Точность расчетов:** Для балансов и сумм транзакций используется строго тип `Numeric(12, 2)` на уровне БД и `Decimal` на уровне Python, что исключает потерю копеек из-за погрешностей чисел с плавающей точкой (`float`).
5. **Разделение слоев (Service Layer):** Роуты в приложении спроектированы «тонкими». Вся бизнес-логика, транзакционность и запросы инкапсулированы в сервисный слой (`service.py`), наследуемый от единого `BaseService`.
